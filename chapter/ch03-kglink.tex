\chapter{Knowledge-enriched Table Understanding with KGLink}
\label{ch:kglink}

This chapter is based on the published paper \emph{KGLink: A Column Type Annotation Method that Combines Knowledge Graph and Pre-Trained Language Model}~\cite{kglink-publication}. We begin our study of structural augmentation by investigating how an existing knowledge graph can supply information missing from a table. We propose KGLink to select candidate types and graph-derived feature sequences, then learn their correspondence to annotation labels through a contextual representation objective.

\section{Motivation and Task}
\label{sec:kglink:motivation}

A table may contain too little context to determine a column type. For example, names of cricket players accompanied by birth and death dates do not reveal their occupation. Linking those names to a knowledge graph can supply occupation and sport relations that are absent from the table.

External knowledge introduces a second difficulty. The type expected by an annotation dataset need not coincide with a type attached to an entity in the graph. A column of basketball players can plausibly be described as \emph{Basketball player}, \emph{Athlete}, or \emph{Name}. An annotation benchmark may use only the last of these labels. A factually relevant graph type alone may therefore leave the required output label ambiguous. The model must learn which description the task expects. KGLink refers to this mismatch as the type granularity gap. The gap includes cases where the desired dataset label does not occupy a convenient ancestor position in the retrieved graph's type hierarchy.

To address these two difficulties, KGLink combines graph processing with supervised representation learning. Graph processing selects relevant external descriptions, while a supervised classifier learns the dataset labels. An auxiliary task trains a contextual representation of the target type so that the classifier can use graph descriptions even when their wording differs from the annotation vocabulary.

We evaluate single-label column annotation on SemTab and modified VizNet. The encoder predicts a dataset label from the cells, table context, and selected graph descriptions.

\section{Problem Formulation and Framework}
\label{sec:kglink:problem}

Let $T$ be a table with row set $R$ and column set $C$. A cell mention $m_c^r$ is the content of row $r$ and column $c$. The task assigns a label $l_c$ from the dataset's type set $D$ to each target column. All columns in the same table can contribute context to that decision. The external knowledge graph supplies entity labels and their one-hop relations. During training, column labels supervise both classification and the auxiliary representation task. During evaluation, those labels are absent from the model input.

KGLink has a graph-processing stage followed by a language-model stage. The graph stage retrieves candidate entities for cell mentions, filters these entities using connections between columns, ranks rows by their linkage quality, and derives candidate types from the remaining entities' neighborhoods. It also constructs a feature sequence for each target column. The language-model stage serializes the processed table, encodes the table and feature sequences, combines the resulting representations, and predicts the column labels. A second training input contains the true type labels and provides contextual supervision for representations generated from masked type positions.

Figure~\ref{fig:kglink:framework} shows the two stages and their training objectives.

\begin{figure}[tbp]
\centering
\includegraphics[width=\linewidth]{figures/kglink/kglink_new_overview.png}
\caption{KGLink's graph-processing and language-model components. Candidate-type text, column feature vectors, and a contextual type-representation objective connect external knowledge to annotation. Original image reproduced from KGLink~\cite{kglink-publication}, Fig.~3.}
\label{fig:kglink:framework}
\end{figure}

Candidate types summarize descriptions supported by linked cells across a column. The feature sequence retains an entity and its neighboring relations from a selected cell. Both enter the learned classifier, which predicts a label from the dataset vocabulary.

Graph descriptions and cell values share the encoder input budget. We therefore select rows before serialization and split wide tables by columns under the input limits.

\section{KG-derived Candidate Types}
\label{sec:kglink:candidates}

\subsection{Cell Mention Linking}
\label{sec:kglink:linking}

The first step retrieves a candidate entity set $E_{m_c^r}$ for each suitable cell mention $m_c^r$ in row $r$ and column $c$. KGLink uses BM25 to score lexical matches between the mention's words and indexed entity labels~\cite{kglink-robertson2009probabilistic}. The implementation indexes Wikidata with Elasticsearch. The score incorporates query-term frequency, inverse document frequency, and label-length normalization. Multiple entities can match the same mention, so the retrieval output is a candidate set rather than a single disambiguated entity.

Short strings are often ambiguous. An album title can match an ordinary word, and a name can refer to several people. We use relationships between cells in the same row to filter these lexical candidates.

Named-entity detection identifies numeric and date mentions, which receive a linking score of zero. Failed lookups also receive zero. The original cell values remain in the encoder input, allowing classification when KG evidence is missing.

We retrieve at most ten entities per cell mention, then apply neighborhood filtering and row ranking before constructing the encoder inputs.

\subsection{Cross-column Neighborhood Filtering}
\label{sec:kglink:filtering}

\begin{figure}[tbp]
\centering
\includegraphics[width=0.76\linewidth]{figures/kglink/KG_part.pdf}
\caption{The original KG-processing pipeline. Cell linking is followed by entity filtering, row selection, and candidate-type generation. Reproduced from KGLink~\cite{kglink-publication}, Fig.~4.}
\label{fig:kglink:kg-pipeline}
\end{figure}

Cells in the same row describe related objects. An album title beside a musician's name supplies a useful relation that either mention lacks in isolation. KGLink uses this relation by checking whether a candidate entity for one cell occurs in the one-hop neighborhood of candidates for another cell in the same row. Let $\mathcal{N}(E)$ denote the one-hop neighbors of a candidate entity set. The filtered set for a cell is
\begin{equation}
\widehat{E}_{m_{c_1}^{r}}
 = \bigcup_{c_2\in C\setminus\{c_1\}}
 \left(E_{m_{c_1}^{r}}\cap\mathcal{N}(E_{m_{c_2}^{r}})\right).
\label{eq:kglink:entity-filter}
\end{equation}
Here $\widehat E_{m_{c_1}^r}$ is the filtered candidate set for the mention in row $r$ and target column $c_1$; $E_{m_{c_2}^r}$ contains the candidates for another column $c_2$, and $\mathcal N$ returns their one-hop neighbors. The union allows support from any other column. The intersection retains entities retrieved for the target mention that also have the required neighborhood support.

Figure~\ref{fig:kglink:overlap} uses \emph{Rust} and \emph{Peter Steele}. A graph connection between an album candidate and the musician candidate supports their interpretation as the entities intended by the row. The role of the edge is to constrain which external facts are relevant to the table. KGLink subsequently associates each retained entity with an overlapping score that counts its neighborhood support from other columns. Entities with more such support contribute more to candidate-type selection.

Filtering depends on both the initial entity candidates and the relations present in the knowledge graph. A missing relation can discard a useful candidate, while an incorrect candidate can survive through a matching contextual link. The encoder also receives the original table values and the separate feature sequence.

\begin{figure}[tbp]
\centering
\includegraphics[width=0.75\linewidth]{figures/kglink/overlap.png}
\caption{Cross-column evidence in the original album-and-musician example. Graph links connect candidate interpretations of cell mentions in the same row. Original image reproduced from KGLink~\cite{kglink-publication}, Fig.~5.}
\label{fig:kglink:overlap}
\end{figure}

Filtering uses relationships between cells in the same row. Candidate-type generation then aggregates recurring descriptions across rows in a column.

\subsection{Row Linking Quality and Input Selection}
\label{sec:kglink:rows}

KGLink derives a cell score from the best-scoring retained entity. For a nonempty filtered candidate set, the score is
\begin{equation}
ls_{m_c^r}=\max_{e\in\widehat{E}_{m_c^r}}ls_e,
\label{eq:kglink:cell-score}
\end{equation}
where $ls_{m_c^r}$ is the score of the mention in row $r$ and column $c$, $\widehat E_{m_c^r}$ is its filtered entity set, and $ls_e$ is the BM25 linking score of candidate entity $e$. Unlinked cells use zero as described in the evaluation protocol. A row's score sums the scores of its cells,
\begin{equation}
ls_r=\sum_{c\in C}ls_{m_c^r}.
\label{eq:kglink:row-score}
\end{equation}
Here $ls_r$ is the linking score of row $r$, $C$ is the column set, and $ls_{m_c^r}$ is the score of its cell in column $c$. Rows are sorted by this quantity, and only the top $k$ rows are retained for prediction.

Linkage ranking favors rows with graph-supported candidates, while taking the first $k$ rows, with the same row budget $k$, follows the source order. The row-filter experiment compares these rules under the same input budget.

The highest-ranked row also supplies the selected cell used for feature-sequence generation. Row ranking therefore changes both the table values and the KG entity passed to the encoder.

\subsection{Candidate Types and Feature Sequences}
\label{sec:kglink:types-features}

Candidate-type generation searches beyond an entity's explicit type attribute. A person's graph entry may be typed as \emph{Human}, while \emph{Musician} appears as an occupation neighbor. The latter can be more informative for a table column. KGLink collects filtered entities across the target column and examines their one-hop neighborhoods. It scores a potential type by aggregating the overlapping scores of entities from other rows that connect to that type. Repeated support within the column increases the candidate's score.

A label-based filter excludes candidates assigned the named-entity schema categories \texttt{PERSON} or \texttt{DATE}. The reported implementation uses spaCy for this step. This filter distinguishes a descriptive candidate type from a particular person's name or a date encountered in the neighborhood. KGLink retains the selected candidate-type labels as text and places them before the cell values in the processed column. The reported implementation generates up to three candidate types per row from the KG entities in each column. Their later contribution depends on how the encoder interprets them in the table context.

If no candidate type is returned, padding occupies the corresponding position. Numeric columns use numeric summary information in this part of the input, while their original values remain available in the table sequence.

The feature sequence provides a second representation of the retrieved knowledge. From the filtered and ranked table, KGLink selects a cell for each target column, chooses its highest-linking entity, and serializes that entity with its one-hop predicates and neighboring entities. If $e$ is the selected entity, $p$ a predicate, and $o$ a neighboring object, the sequence consists of the entity label followed by predicate--object descriptions. Encoding this text yields a feature vector for the column. A padding sequence is used when the column has no retrieved entity.

\section{Language Model Integration}
\label{sec:kglink:language-model}

\subsection{Table Serialization and Column Representations}
\label{sec:kglink:serialization}

KGLink adapts the multi-column serialization used by Doduo~\cite{kglink-suhara2022annotating}. A special \texttt{[CLS]} token begins each column's segment. The segments are concatenated into one input sequence, followed by a \texttt{[SEP]} token. The contextual representation at each column's \texttt{[CLS]} position provides that column's vector. Because the sequence contains multiple columns, self-attention can use information outside the predicted column.

For table $T$ with column set $C$, write the tokenized contents of column $i$ as $\mathrm{tok}_i^1,\ldots,\mathrm{tok}_i^{m_i}$, where $m_i$ is its token count. The serialized sequence $S(T)$ has the form
\begin{equation}
\begin{split}
S(T)={}&[\mathrm{CLS}]\ \mathrm{tok}_1^1\cdots\mathrm{tok}_1^{m_1}\quad
[\mathrm{CLS}]\ \mathrm{tok}_2^1\cdots\\
&[\mathrm{CLS}]\ \mathrm{tok}_{|C|}^1\cdots\mathrm{tok}_{|C|}^{m_{|C|}}\quad
[\mathrm{SEP}].
\end{split}
\label{eq:kglink:serialization}
\end{equation}
Each column's \texttt{[CLS]} position produces a contextual vector using the serialized columns. Candidate-type text precedes the corresponding cell values, allowing both to interact with neighboring columns through self-attention. KGLink separately encodes the feature sequence into a column-specific vector and combines it with the contextual column vector through the composition function $\phi_{\mathrm{comp}}$, shown as $\phi$ in Figure~\ref{fig:kglink:framework}. The resulting representation is mapped into the dataset's classification space.

The principal experiments fine-tune BERT~\cite{kglink-devlin2018bert}. The model has a sequence limit of 512 tokens; the reported implementation limits each column to 64 tokens and each encoded table to eight columns. Tables with more columns are divided after candidate-type generation and are encoded separately. These limits define the context available to the classifier. In particular, retaining 25 table rows does not imply that every token in those rows survives serialization, since tokenization and the column limit also constrain the final sequence.

\subsection{Contextual Type Representation Learning}
\label{sec:kglink:representation}

The auxiliary task trains a type representation at a masked position. During training, KGLink constructs two versions of the processed table. The ground-truth version places the annotated type label before the candidate types in each target column. The masked version replaces that label with \texttt{[MASK]}. Both versions retain the column values and candidate-type context. Encoding the two sequences produces contextual representations for the true type and its masked counterpart.

Figure~\ref{fig:kglink:representation} illustrates the two inputs and their contextual outputs.

\begin{figure}[tbp]
\centering
\includegraphics[width=\linewidth]{figures/kglink/dmlm.png}
\caption{Contextual type-representation training with masked and ground-truth table inputs. The true-type table is constructed during training. Original image reproduced from KGLink~\cite{kglink-publication}, Fig.~6.}
\label{fig:kglink:representation}
\end{figure}

The paired inputs teach the encoder how the label relates to the table context. A label such as \emph{Musician} is encoded together with the column values and graph-derived descriptions, rather than as an isolated word. The masked input must produce its type representation from the evidence that will be available at prediction time. Distilled masked language modeling provides the auxiliary objective~\cite{kglink-wang2020learning}. The model projects contextual representations into vocabulary space with a temperature parameter, then uses the ground-truth and masked outputs in the reported training loss.

With contextual vector $H$ and temperature $\mathcal{T}$, vocabulary projection gives
\begin{equation}
Y=\operatorname{Softmax}\!\left(W_o\frac{H}{\mathcal{T}}\right),
\label{eq:kglink:vocabulary-projection}
\end{equation}
where $W_o$ projects the contextual vector $H$ into vocabulary space, $\mathcal T$ is the temperature, and $Y$ is the resulting probability vector. Denote the masked and ground-truth outputs by $Y_{\mathrm{msk}}$ and $Y_{\mathrm{gt}}$. The main paper writes the auxiliary objective as
\begin{equation}
\mathcal{L}_{\mathrm{DMLM}}(Y_{\mathrm{msk}},Y_{\mathrm{gt}})
=-\sum_{j=1}^{V}y_{\mathrm{msk}}^{j}\log y_{\mathrm{gt}}^{j},
\label{eq:kglink:dmlm}
\end{equation}
where $V$ is the vocabulary size and $y_{\mathrm{msk}}^j$ and $y_{\mathrm{gt}}^j$ are the $j$th components of the masked and ground-truth output vectors, respectively. The objective uses the contextualized representations produced from the two table inputs.

Training uses both true-type and masked inputs; evaluation uses the masked input. The model thus learns from annotated types during training and predicts from table values and retrieved descriptions at inference, including for numeric columns and columns without KG candidates.

The shared encoder is trained jointly for dataset-label classification and vocabulary-space type representation. The classification head produces the final column label.

\subsection{Classification and Adaptive Task Weighting}
\label{sec:kglink:objective}

Let $z_c$ be the classification logits obtained from the combined column and feature representations. For a target label $l_c$, the classification loss is cross-entropy,
\begin{equation}
\mathcal{L}_{\mathrm{CE}}(z_c,l_c)
 =-\log\frac{\exp(z_{c,l_c})}{\sum_{j\in D}\exp(z_{c,j})}.
\label{eq:kglink:classification}
\end{equation}
Here $z_{c,j}$ is the logit for label $j$ in the dataset label set $D$, and $z_{c,l_c}$ is the logit for the target label $l_c$ of column $c$. KGLink jointly optimizes this loss and the auxiliary representation objective using uncertainty weighting~\cite{kglink-kendall2018multi}. With trainable task parameters $\sigma_0$ and $\sigma_1$, the combined objective is
\begin{equation}
\mathcal{L}_{\mathrm{total}}
 =\frac{\mathcal{L}_{\mathrm{CE}}}{2\sigma_0^2}
  +\frac{\mathcal{L}_{\mathrm{DMLM}}}{2\sigma_1^2}
  +\log(\sigma_0\sigma_1).
\label{eq:kglink:joint-loss}
\end{equation}
Here $\mathcal L_{\mathrm{total}}$ combines classification loss $\mathcal L_{\mathrm{CE}}$ and representation loss $\mathcal L_{\mathrm{DMLM}}$, with trainable parameters $\sigma_0$ and $\sigma_1$, respectively. This indexing follows Figure~\ref{fig:kglink:framework}; the source equation assigns the two indices in the opposite order. The temperature used in the representation objective is set to two in the reported experiments.

The trainable task weights balance the representation and classification losses during optimization.

\section{Computational Structure}
\label{sec:kglink:complexity}

The graph-processing cost depends on table dimensions, candidate-set sizes, and neighborhood sizes. Linking traverses table cells. Cross-column filtering compares candidate information between columns within a row. Candidate-type scoring visits neighborhoods and aggregates support across rows. The implementation's limits on retrieved entities and serialized columns constrain these operations in the evaluated setting. The external Wikidata index is prepared with Elasticsearch and supplies lexical retrieval scores.

Let $n_R$ and $n_C$ be the maximum numbers of rows and columns per table, $n_T$ the number of tables, $n_E$ the maximum number of retrieved entities per mention, and $n_N$ their maximum one-hop neighborhood size. In these count symbols, the original analysis reports the preprocessing expression
\begin{equation}
O\!\left(n_R n_C n_E(n_N+n_C n_E n_T)\right).
\label{eq:kglink:preprocessing}
\end{equation}
Neighborhood aggregation and cross-column candidate filtering contribute to preprocessing. Increasing the candidate-set limit adds graph work even when the encoder input remains capped.

Encoding cost depends on the serialized input length and the encoder's hidden dimension. KGLink encodes table inputs and column feature sequences; training also includes the ground-truth and masked constructions used by the representation task. The classification head maps column vectors into the label space, while the auxiliary projection operates over the language model's vocabulary. Thus, increasing the label set affects classification, whereas increasing the vocabulary-space projection concerns the representation objective.

Reducing the row count need not shorten a sequence already truncated to its token limit. Graph preprocessing and encoder computation can therefore respond differently to the same input-selection change.

\section{Experimental Evaluation}
\label{sec:kglink:experiments}

\subsection{Datasets and Protocol}
\label{sec:kglink:protocol}

The evaluation uses SemTab 2019 and a modified VizNet subset~\cite{kglink-hassanzadeh_oktie_2019_3518539,kglink-zhang2020sato}. SemTab includes tables derived from Wikipedia, DBpedia, and the T2Dv2 Gold Standard sources. The experiment uses rounds 1, 3, and 4, with 3,048 tables, 7,587 columns, and 275 column types. Round 2 has columns with multiple ground-truth labels and is excluded from this single-label comparison. The reported averages are 69 rows and 4.5 columns per table.

The modified VizNet corpus targets column annotation rather than the full range of visualization tasks in the original repository~\cite{kglink-hu2019viznet}. The experiment uses its multi-column portion so that methods can exploit relations between columns. Its annotation scheme is coarser than SemTab's and includes numeric types. The evaluated portion contains 32,265 tables, 73,034 annotated columns, and 77 types.
% Dataset prose: 73,034 columns; source Table III: 74,141 columns.
% Do not select a denominator or recompute the original percentages.

The data are split into training, validation, and testing portions in the ratio 7:1:2 while maintaining each class's original sample proportion. Each experiment is averaged over three runs. Accuracy measures exact label prediction, and weighted F1 weights class-level performance by sample frequency.

Training uses AdamW with optimizer parameter $\epsilon=10^{-6}$ and an initial learning rate of $3\times10^{-5}$. The learning rate decays linearly without warm-up. The reported maximum training lengths are 50 epochs on SemTab and 20 on VizNet, with early stopping. Batch size is 16 for both datasets; dropout is 0.1 for SemTab and 0.2 for VizNet. The implementation uses PyTorch and the Transformers library on an NVIDIA Tesla V100 GPU.

The baseline set includes MTab, TaBERT, Doduo, HNN, Sudowoodo, and RECA~\cite{kglink-2021_mtab4wikidata,kglink-yin2020tabert,kglink-suhara2022annotating,kglink-chen2019learning,kglink-wang2022sudowoodo,kglink-sun2023reca}. TaBERT and Doduo use KGLink's experimental settings. HNN and RECA follow their original settings. Sudowoodo receives the full labeled training set in this comparison. VizNet labels are translated to Wikidata entities for MTab, and MTab's weighted F1 is unreported because of the difference in problem definition.

\subsection{Type Granularity in the Reported Cases}
\label{sec:kglink:qualitative}

Among SemTab classes with more than ten test samples, Athlete, Protein, and Film have the three largest reported accuracy increases when the representation-generation task is added.

Protein columns can retrieve KG descriptions such as Gene or Enzymes, while Film columns can retrieve Television series, Scholarly article, or Book. These descriptions are related to the cell values but differ from the annotation labels. The contextual representation task learns how to use them jointly with the column contents.

The Athlete example shows the same granularity gap. KGLink retains the graph description as input and learns the annotation category from supervised examples.

\section{Discussion and Chapter Summary}
\label{sec:kglink:discussion}

We proposed KGLink to supply missing table context and learn the correspondence between graph descriptions and annotation labels. Cross-column filtering selects entity candidates, recurring neighborhoods supply candidate types, and the contextual representation objective trains the encoder to use this information.

Removing either the masked representation task or KG information lowers the full BERT configuration's annotation scores. Linkage-based row selection also improves the results. On tables without retrieved KG evidence, the trained encoder continues to annotate from the table values.

KGLink's external evidence is limited to the entities and relations available through linking and neighborhood retrieval. Its supervised predictor learns the training label set, and the experiments use single-label annotation with bounded table inputs.

To support tasks without a suitable knowledge graph or sufficient fine-tuning data, we next investigate constructing a graph from task examples and retrieving candidate labels for a large language model. Chapter~\ref{ch:gorag} develops this approach for dynamic few-shot classification.
